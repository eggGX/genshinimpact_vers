# フレンド対戦・Phase 1：Firebaseルーム接続

この段階では**ルーム作成・参加・接続状況の確認のみ**が動作します。
カード使用、攻撃、ターン交代、マリガン、勝敗はまだオンライン同期されません。
既存のローカル対戦は変更していません。

## Firebaseの準備

1. [Firebase Console](https://console.firebase.google.com/) でプロジェクトを作成する
2. Authentication → Sign-in method で **匿名（Anonymous）** を有効化する
3. Firestore Database を作成する（本番モード推奨）
4. Firestore → ルール画面に、リポジトリ直下の `firestore.rules` を貼り付けて**公開**する
5. Firebaseプロジェクトの **プロジェクト ID** と **ウェブ API キー** を確認する
6. プロジェクト直下に `.env.local` を作り、次の2項目を設定する

```dotenv
VITE_FIREBASE_PROJECT_ID=your-project-id
VITE_FIREBASE_API_KEY=your-web-api-key
```

7. `npm run dev` を再起動する
8. デッキ選択画面の「フレンド対戦（ルーム作成・参加）」から進む

`VITE_*` の値はブラウザに公開されるクライアント設定です。**Firebase サービスアカウント秘密鍵や管理者用認証情報を入れないでください。**
匿名認証のIDはブラウザの `localStorage` に保存します。同じブラウザで更新すれば同じルームを認識できます。ブラウザのデータを消すと匿名IDが失われるため、作成済みルームの参加者として扱えなくなる場合があります。

## テスト

- ブラウザ A でルーム作成してコードをコピー
- ブラウザ B（別のブラウザプロファイルまたは別PC）でコードを入力して参加
- 約2.5秒ごとに参加状態を更新
- ルームは Firestore の `friendRooms` コレクションに保存
- 「ロビーを離れる」は画面を閉じる動作だけで、サーバー上の参加枠は解放しません

## 制約と次の段階

- ルーム参加状況は**接続生存確認ではありません**。参加済み表示はゲスト枠が埋まったことを表します。
- ルームは自動削除されず、古いルームが残ります。運用開始前にクリーンアップ方法を検討します。
- Firebaseへの通信が可能で、Firestoreのルールが公開されている必要があります。
- **手札・山札の中身をこのルームドキュメントに保存してはいけません。**
- 現状のゲームエンジンはプレイヤー2人分の完全状態を同じブラウザで管理し、ランダム処理をクライアントで行います。**そのまま共有すると不正な情報閲覧・状態改変が可能になります。**
- 次の Phase 2 では、サーバー側でゲーム状態・ランダム処理・行動検証を管理し、プレイヤーごとに公開可能な情報だけを配信する構成へ移行します。

## Phase 2（準備完了の同期）

ルームに2人が参加すると、それぞれが自分のデッキを選んで「準備完了」を押せます。
相手の準備状態は約2.5秒ごとに反映されます。
「準備完了」を押すと、40枚のデッキを各自の非公開ドキュメントへ登録してから準備フラグを更新します。
相手にはデッキを読み取る権限がありません。

この段階では、準備完了後もオンラインでゲームは開始されません。
対戦エンジンのホスト化、双方のカード操作の検証、相手の非公開情報の保護が必要です。

### 更新分の反映手順

```bash
git pull
npm run build
npx firebase-tools deploy --only firestore:rules,hosting
```

前バージョンのFirestoreルールでは準備状態を更新できないため、**ルールのデプロイも必須**です。

### 無料プランについて

Firebase Sparkプラン上では、Firebase Cloud Functionsのようなサーバー側の実行基盤をそのまま利用できない場合があります。
サーバー権威のある対戦処理を実装する場合は、別の実行基盤またはプランの選択が必要です。
手札・山札をFirestoreの公開可能なルーム文書へ保存しないでください。

## Phase 3：対戦セッション開始の同期

両者が準備完了したら、ホストだけに「対戦セッションを開始」が表示されます。
押すとFirestoreの `friendRooms/{code}.status` が `playing` になり、
参加中のゲストの画面も約2.5秒以内に対戦セッション画面へ切り替わります。
同時の準備取り消しを防ぐため、開始更新はFirestoreの更新時刻を条件にし、
セキュリティルールでもホスト本人・ゲスト参加済み・両者準備完了を要求します。

現在の開始画面は **通信の確認用** であり、ローカル対戦エンジンは起動しません。
オンラインのマリガン、手札・山札の生成と秘匿、ターン制御、カード操作の検証・同期は未実装です。
ゲーム本体を公開文書に置く設計に変更しないでください。

参加者のブラウザでは最後のルームコードを記憶し、同じ匿名IDで再度フレンド対戦画面を開くとルームを復元します。
ルームを明示的に離れる操作で記憶を消します。

### 反映コマンド

```bash
git pull
npm run build
npx firebase-tools deploy --only firestore:rules,hosting
```

新しい `playing` 状態の書き込みを許可するため、Firestoreルールの再デプロイが必須です。

## Phase 4：各プレイヤーのデッキを非公開で提出

Firestoreの `friendRooms/{code}/privateDecks/host` と
`friendRooms/{code}/privateDecks/guest` は、それぞれの所有者だけが読み取り可能です。
対戦相手は、コードを知っていても他人のデッキを読めません。

- 準備完了時に40枚のデッキと元素構成を登録し、登録が成功してから準備状態を変更します
- 準備完了中や対戦開始後はデッキを書き換えられません
- デッキが提出されていない場合は準備完了・対戦開始をFirestoreルールが拒否します
- **現段階のFirestoreルールはカード枚数や所有者を検査しますが、カードの正当性を完全に検証するものではありません。**
  本番では権限のあるゲームサーバーがカード定義、元素制限、最大枚数、シャッフルを検証する必要があります
- 対戦相手の手札・山札は、現段階で作成も同期もしていません

### 更新コマンド

```bash
git pull
npm run build
npx firebase-tools deploy --only firestore:rules,hosting
```
